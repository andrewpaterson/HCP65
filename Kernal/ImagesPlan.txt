Images plan
===========

A program draws sprites from flat images: each a width x height of pixel bytes in the program's own memory, which a
Blitter Board or the Graphics Board copies from.  The Graphics Board needs flat rows to stretch and shrink a sprite (its
offsets index a row), which SFT's runs aren't.  So the program unpacks an SFT once into a flat image, gives the kernal
the image (it gets a handle), frees its SFT, and blits by the handle.  A pixel is a byte: an index into one of the
Video Board's 128 palettes.  SFT blits stay, for the console's font and images drawn once.


Stage 0: the SFT format (done)
------------------------------
CommonLibraries c6af740c3, HCP65 317139a.  Every SFT record starts with the magic number "SF", the layout's version
(SFT_VERSION, 1) and its type: 1 opaque, 2 transparent, 3 container, 4 palette.  A record of another layout isn't read.

A palette record is a first index, a count of 1 to 256 colours, and an FNV-1a hash of the first index, the count and
the colours, then that many reds, greens and blues.  Palettes are often smaller than 256 colours, and several small ones
can share one of the board's palettes at different indices.  Palettes with the same hash are very likely the same, so
the images that use them can share a board palette.  In a container a palette is the palette of the images after it.

KernalScreenSetColours takes a palette record and loads its colours at its indices, leaving the rest of the board's
palette as it was.  SFTColours makes the record of the 3-3-2 colours that a pixel with no palette is.


Stage A: images, and blits of them (done)
-----------------------------------------
HCP65 c1d6d3b.  The calls are KernalScreenAddImage and KernalScreenRemoveImage, a full table is
KERNAL_DEVICE_NO_HANDLES and a handle that isn't the program's KERNAL_DEVICE_BAD_HANDLE.
Where an image is: in the program's own heap (malloc), so its memory is the program's and goes when it ends.  The
kernal keeps only a handle to it.

  UserLib (in the program)
    SFTImageMake(pvSFT, uiSize, uiPalette, &uiImage)
                    mallocs the image's width x height bytes, unpacks the SFT into them on the processor (what a
                    transparent image doesn't draw is SFT_PIXEL_TRANSPARENT, 0) and gives the kernal the image.  The
                    program can free its SFT then.
    SFTImageFree(uiImage)
                    takes the handle back from the kernal, then frees the image's memory.

  The kernal (screen calls)
    KernalScreenAddImage(pvPixels, uiWidth, uiHeight, uiFlags, uiPalette, &uiImage)
                    keeps the image's address, size, whether it is transparent and the board palette its pixels are
                    drawn with (KERNAL_SCREEN_NO_PALETTE: pixels keep the palette they have).
    KernalScreenRemoveImage(uiImage)
                    the handle goes.

  KERNAL_BLIT_IMAGE (SKernalBlit's uiFlags)
                    uiImage is a handle, not an SFT's address.

The images are a table of 64 in MPU RAM (the drivers read it while a board has main memory).  A handle is the table
entry's index and a generation that counts each time the entry is used again, so a handle that has gone, or another
process's, is refused (KERNAL_DEVICE_BAD_ARGUMENT); no entry left is KERNAL_DEVICE_NO_MEMORY.  When a process ends,
CKernalScreen::ProcessEnded drops its handles.

A blit of an image is a copy for each row's part inside the clip rectangle (KernalMainCopy: the Blitter Board's, or
the Graphics Board's with the offsets 0, 1, 2..., for long rows, the processor's for short ones), transparent leaving
0 out.  The image's addresses are the program's, found again at each blit (KernalUserPointer), as the program's banks
aren't next to each other in main memory: a row that crosses from one of the program's banks to the next is two copies,
the second from the next bank's place in main memory.  A bank the program no longer has is refused, not a fault.  If the
program frees an image's memory without SFTImageFree, what is drawn is whatever is there: that is the program's to get
right.

Tests: a program makes opaque and transparent images, blits them whole, clipped and across a bank, and the host
compares the frame with what it works out; handles that have gone, another process's and a full table are refused; the
handles are dropped at the end.


Stage A2: stack and NULL canaries (done)
----------------------------------------
HCP65 9a4ddb4.  The results are KERNAL_RESULT_STACK_OVERFLOW and KERNAL_RESULT_NULL_WRITE; the check is about 200
cycles a call.
Not about images: put here, after stage A, to be done next.  A user program's wild pointers into a bank it doesn't
have reach physical bank 0, which is no one's, so they do no harm, but nothing notices
(Kicad/Computer/Processor/Processor Board/Bad Access Detection.txt is a hardware way to).  Two common mistakes stay
inside the program's own bank 0, which is always mapped, and software can catch them:

  Stack             a pattern at the bottom of the stack area (its lowest bytes, above which the stack mustn't grow).
  NULL              the bottom of bank 0 kept unused and filled with a pattern: a NULL pointer's reads and writes land
                    there.  The direct page and anything else the start up puts at the bottom of bank 0 move up.

The kernal writes both when it loads the program and compares them at each kernal call (COP) and when the program
ends.  A changed canary ends the program with a new result, KERNAL_PROCESS_STACK_OVERFLOW or KERNAL_PROCESS_NULL_WRITE.
It costs a few dozen cycles a call against about 2900 for the call itself.  It doesn't say which instruction did it,
only that it happened since the last call.

Tests: programs that overflow their stack and write through NULL are ended with those results; one that does neither
runs as before; the cost of a call is measured with TEST_HCP65_TIME_COP before and after.


Stage B: scaled blits (Graphics Board) (done)
---------------------------------------------
HCP65 2cb838c.  About 9000 cycles a blit and 1000 a row; with the row loop in assembly (KernalMainScaledRows) about
10000 a blit and 550 a row.
KERNAL_BLIT_SCALED with uiWidth and uiHeight (SKernalBlit +26 and +28): the image drawn at that size.

  Across            each drawn row is one copy, the offsets mapping each pixel drawn to the image pixel it is (the
                    nearest), transparent leaving 0 out.  The offsets are written only when the drawn width or the clip
                    changes: the kernal knows which are in the board.
  Down              each drawn row's image row is its source address.
  Across a bank     two copies: the second with the source address set so that the source address plus the offset is
                    in the next bank's place in main memory.
  Mirrored          KERNAL_BLIT_MIRROR_X (offsets going backwards) and KERNAL_BLIT_MIRROR_Y (rows from the bottom).
  Limits            a drawn row is no more than 32767 pixels (the count is 15 bits); an image row no more than 64KB
                    (the offsets are 16 bits).
  No Graphics Board KERNAL_DEVICE_NOT_FOUND.

Tests: 1:1, x2, x1/2 and odd ratios, mirrored, clipped on each side and across a bank, against the host's nearest
pixel.  Measured: the cycles a row and the cost of writing the offsets.


Stage Q: palettised images from PNGs (host) (done)
--------------------------------------------------
CommonLibraries 5b71818a1: SupportLib's QuantiseSFT and SaveSFTQuantised, and Tools/PNGToSFT.
SupportLib gets a quantiser from a CImage (PNG, BMP and the others) to pixels and a palette: the image's own colours
when there are few enough, else median cut to the most colours it is given, using as few as the image needs, without
dithering.  Several images can be made one palette (an animation's frames).  A pixel whose alpha is below half is
transparent (0); 0 isn't a colour of a transparent image's palette.  The SFT writer writes a container of the palette
and its images, and a command line tool makes an SFT from PNGs.


Stage C: the Sprites demo and the docs (done)
---------------------------------------------
The stage and the flower are images; Maki's frames stay SFT blits (her palette in palette 1), as without a Blitter
Board her transparent frame is 455000 cycles as an image and 144000 as an SFT (the user chose to keep the SFT); with a
Graphics Board she is drawn small, scaled and mirrored, from an image.  memory-map.md has a program's memory.
Sprites draws a palettised sheet through images, a sprite of it scaled.  Docs/hcp65/screen.md gets images and
scaled blits, and the kernal's memory calls are documented with them.  Measured: an image blit against an SFT blit.
