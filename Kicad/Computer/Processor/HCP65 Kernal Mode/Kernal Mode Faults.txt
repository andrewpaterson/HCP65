HCP65 Kernal Mode - schematic faults
====================================

What the board is meant to do (the user, 2026-11-20): an interrupt's vector
pull (~VP low) puts the processor board in kernel mode only at the vector
access, so all of the interrupt's stack work is done in user space, on the
process's own stack in its own bank 0; RTI takes it back out of kernel mode
before any of its stack work.  The count of interrupts is zero in user mode
and above zero in kernel mode, and kernel mode is forced until the Native
Latch is set (the boot's reset vector).  Every process's bank 0 holds the
same vectors as the kernal's, because the vector's first byte is read in
user mode.  The emulator and the kernal follow that (HCP65Lib/HCP65.cpp,
Kernal/KernalProcess.cpp).

1. Kernal Mode PART is the count being 127, not above zero (IC2)

   IC2 is a 74LVC11, a triple 3-input AND: 1Y (pin 12) is C0.C1.C2, 2Y
   (pin 6) is C3.C4.C5, and 3Y (pin 8) is 1Y.2Y.C6, which is Kernal Mode
   PART.  So it is high only when all seven bits of the count are set.

   Effect: the count is 1 after an interrupt from user mode, so the board
   doesn't see kernel mode: the bank byte stays remapped and the vector, the
   kernal's code and its data are all read from the process's banks.

   Fix: the same three gates as ORs, wired as they are, so Kernal Mode PART
   is (C0+C1+C2)+(C3+C4+C5)+C6, the count above zero.  For example three
   74LVC1G332s (single 3-input OR, 3.3V and 5V tolerant, so they take the
   74HCT193s' 5V outputs), or a 74HC4075 (triple 3-input OR, a different
   pinout from the 74LVC11's) powered from 5V, whose output the 3.3V parts
   it drives (IC6, a 74LVC04) tolerate.

2. Kernal mode is held off once the Native Latch is set, not forced before
   it (IC1)

   IC1 is a 74LVC1G02 (NOR) of ~{Kernal Mode}_PART (pin 2) and Native Latch
   (pin 1): Kernal Mode (pin 4) is Kernal Mode PART and not Native Latch.
   Before the latch is set that follows the count (which the reset's vector
   pull only makes 1 too late for the reset vector); after it, Kernal Mode
   is low whatever the count is.

   Effect: once the boot has gone native the board is never in kernel mode.
   Before then it is only in kernel mode when the count says so, which isn't
   in time for the reset vector to come from the MPU Memory Board.

   Fix: a NAND in IC1's place, a 74LVC1G00 (the same SOT353 pinout as the
   74LVC1G02: A pin 1, B pin 2, Y pin 4), so Kernal Mode is Kernal Mode PART
   or not Native Latch: forced before the latch is set, the count after.

3. The bank byte switches a cycle before the rest of the board's mode does
   (IC7, IC8)

   IC7's first half (the remap latch: 1~{OE} pin 1) and IC8 (the bank byte
   straight through: ~{OE1} pin 1, ~{OE2} pin 19) are switched by the Kernal
   Mode net and ~{Kernal Mode} (IC6 pin 6): the count decoded straight
   away.  The rest of the processor board takes Kernal Mode OUT and ~{Kernal
   Mode} OUT, which IC13 latches from the same net at the end of each cycle
   (CP is ~{PHI2}).  So in the first cycle of a vector pull, as soon as ~VP
   counts the count up, the bank byte goes to the processor's own ($00)
   while the memory boards still see user mode, and likewise at an RTI the
   other way round.

   Effect: the vector's first byte is read from bank 0 of main memory (a
   bank no process has: a remap page can't name it), not from the process's
   own bank 0 with its copy of the kernal's vectors, so an interrupt from
   user mode jumps to a wrong address.  Which byte wins depends on the
   gates' delays against the access, so it can come and go.

   Fix: switch IC7 and IC8 with the latched mode, so the bank byte and the
   decode change on the same edge: IC7's 1~{OE} (pin 1) from Kernal Mode OUT
   (IC13 Q, pin 5) and IC8's ~{OE1} and ~{OE2} (pins 1 and 19) from ~{Kernal
   Mode} OUT (IC13 ~{Q}, pin 3).  The vector's first byte then comes from
   the process's bank 0 and its second from the kernal's, as intended, and
   RTI's pulls are all in user mode.  IC6's third inverter (pins 5 and 6) is
   then spare.


Found in the daughter board review of 2026-11-23 (faults 1 to 3 above are
all still in the schematic)
-------------------------------------------------------------------------

4. IC10's symbol has the 74LVC00's pinout, not the 74LVC02's

   The symbol 74LVC02APW,118 in Symbols/Nexperia.kicad_sym numbers its pins
   like a '00 (1A=1, 1B=2, 1Y=3, 2A=4, 2B=5, 2Y=6, 3Y=8, 3A=9, 3B=10, 4Y=11,
   4A=12, 4B=13).  The real 74LVC02A is 1Y=1, 1A=2, 1B=3, 2Y=4, 2A=5, 2B=6,
   3A=8, 3B=9, 3Y=10, 4A=11, 4B=12, 4Y=13.

   Effect, with the real part fitted:
   - Pins 10 and 13 (3Y, 4Y) drive the Processor Board's global ~{WD},
     fighting the Breakout's IC19, so every write in the machine is affected.
   - Pin 1 (1Y) drives ~{Process ID} against the MPU Address Decode board's
     Register8 output, and pin 4 (2Y) drives ~{Interrupt Depth} against
     Register9 (which also reaches the counters' ~PL through IC3 pin 12).
   - Pins 3 and 6 sit on /Read Process ID and /Read Interrupt Depth, which
     nothing then drives, so IC6 pins 9 and 11 float and IC4 drives D0-D7 at
     random.
   - Pin 8 sits on /Write Process ID, so IC7's 2LE (pin 25) floats and the
     Process ID latch takes random values.  Pin 11 (4A) is unconnected.

   Fix: correct the symbol's pin numbers (it is also used by Device Reset,
   Instruction Code, MPU NMI, Device Decode stage A/B and Processor Full
   Device) and re-route IC10.

5. The interrupt depth counters are held clear (IC9, IC5)

   The 74HCT193's MR (pin 14 on both) is active high, but it is on ~{Reset}.

   Effect: both counters are held at zero for as long as the machine is out
   of reset, so the count is always zero.

   Fix: MR from an active-high Reset, for example IC10's spare gate 4 as
   NOR(~{Reset}, ~{Reset}) once IC10 is re-routed, or IC6's third inverter
   once fault 3 is fixed.

6. The counters' clocks idle low (IC9 pins 4 and 5)

   CPU (pin 5) is Enter Interrupt (VP inverted by IC6) and CPD (pin 4) is
   RTI.  Both are low except during their own events.  A 74HCT193 counts up
   on CPU's rising edge only while CPD is high, and down on CPD's rising edge
   only while CPU is high.

   Effect: neither direction counts, and the ~{TCU} and ~{TCD} cascade
   outputs into IC5 are wrong too.

   Fix: both clocks must idle high.  Feeding ~{VP} and an active-low RTI in
   directly would count on the end of each pulse instead, which for RTI is
   after its stack pulls and breaks the "RTI pulls in user mode" scheme.  A
   synchronous up/down counter with count enables (a 74LVC169-type part,
   clocked from ~{PHI2}) driven by edge-detected VP and RTI avoids that.

7. Back to back RTIs count down only once

   RTI is a level decoded from the latched opcode (OP0-OP7 from the
   Instruction Code board), so it stays high across two RTI opcodes in a
   row.  This happens with nested interrupts, for example an NMI taken just
   before an IRQ handler's RTI returns straight onto that RTI.

   Effect: the count is left at 1 after returning to user code, so the board
   stays in kernel mode.

   Fix: count down on each opcode fetch whose opcode is $40 (Opcode Valid
   qualified with the decode), not on the RTI level.  Note that OP0-OP7 are
   themselves a cycle late and miss some fetches today (Instruction Code
   Faults.txt).

8. IC13 has no power (74LVC2G74, pin 8)

   IC13's VCC pin 8 is on GND, on the schematic and the PCB.  Pin 4 is GND
   as well.

   Effect: the flip-flop is only phantom-powered through its inputs, so
   Kernal Mode OUT and ~{Kernal Mode} OUT are invalid.

   Fix: connect pin 8 to 3.3V.

9. Possible: A_OUT16-23 have two drivers for an instant when the mode
   changes (IC7, IC8)

   IC7's first half is enabled by Kernal Mode and IC8 by the same signal
   through an inverter, so both drive KA16-23 for an inverter delay.  This
   is still so after fault 3's fix, as Q and ~{Q} switch a few ns apart.

   Fix: accept it, or make the switch break-before-make.

10. Possible: the remap latch closes on the same edge that ends the lookup
    (IC7)

    IC7's 1LE is ~{PHI2}, so the remap byte is latched on the same edge that
    switches the Selector 12bit boards back to the processor's address and
    that enables the Breakout's data transceiver (its DE is PHI2 directly,
    while ~{PHI2} lags it by an inverter).  The data hold is only the '157's
    delay plus the SRAM's tOH (about 3ns) against the 74LVC16373's hold
    time, and on a write cycle the transceiver can start driving the
    processor's bank byte onto D0-D7 before IC7 has closed.

    Fix: close the remap latch earlier than the bus turnaround, for example
    with a PHI2-derived signal that leads DE, or delay the transceiver
    enable.
