Documentation, website and Claude (DocsPlan.txt, plan, 2026-11-24)
==================================================================

The user (2026-11-24): "Plan out the documentation / website / claude integration ... plan".  It follows a
discussion the same day: "The IDE needs to treat those markdown docs as essentially a part of the code?", "How do
high level designs tie in?" and "can this become something that Claude can be pointed at?".

Nothing here is a go-ahead: the decisions under "Decided" are the user's, everything else is proposed, and each
stage says what of it is built.  The questions under "What is the user's to decide" are asked one at a time, my recommendation first.


The goal
--------

One set of documentation that is part of the code: written in the repositories next to what it describes, built and
checked like code, kept right by the IDE's refactorings, and readable by people (the website), by the IDE and by
Claude.  The rule underneath it all: the C++ index (CppCompilerLib's CCPPIndex) decides what a reference in a page
means, the same code for the IDE (live, while editing) and for the website build (in a batch), so they can never
disagree.


What there is to build on (surveyed 2026-11-24)
-----------------------------------------------

The website (HCP65/Website):
  - MkDocs + Material, built by web.sh (build, serve, live) with its own .venv (mkdocs-material, glightbox,
    table-reader, openpyxl).  `mkdocs build --strict` passes.  84 pages: 65c64 33, ide 25, hcp65 13, compiler 11,
    libraries 1.  The pages name source files in backticks but link to none.
  - Checks: tools/check_instruction_tables.py (the 65C64 instruction index against the instruction pages; web.sh runs
    it) and TestAssembler65Lib's TestAsm65C64Website.cpp, which assembles every ```asm block under docs/65c64.
  - Generated: only docs/65c64/opcode-encoding.md, by tools/sheet_to_html.py from the spreadsheet's 'Opcode encoding'
    sheet, run by hand (web.sh doesn't).  pymdownx.snippets has one base_path (TestAssembler65Lib's Input) and one
    page uses it (examples.md).
  - All four repositories are public on GitHub (CommonLibraries = Codaphela.Library, HCP65, HCP65-IDE, LogiCim =
    Codaphela.LogiCim), so links to the code work for anyone.

The IDE (HCP65-IDE):
  - VisualStudioLib reads ClCompile, ClInclude, None, Text, Image and CustomBuild items (VcxItem.cpp); no sign of
    wildcard Include support.  Libc65.vcxproj is a Makefile project with no commands (indexed, never built).
  - BuildLib builds a whole solution with one toolchain: HCP65, MSVC or GCC (SolutionBuild.h).  Nothing runs a
    Makefile project's NMakeBuildCommandLine.  CCommandBuild (CommandBuild.h) runs programs one after another and
    collects their output: a subclass says what to run.
  - The Build pane and Problems list understand "<file> (<line>, <column>): ", MSVC's "<file>(<line>,<column>): " and
    GCC's "<file>:<line>:<column>: <kind>: " (CIDEMessageOutput::ParseMessageLine), so a check that prints GCC's form
    gets clickable rows for nothing.
  - Rename's text search covers .txt and .md items of the solution's projects (IDERename.cpp:267); files outside the
    solution aren't searched (a gap listed in the IDE notes).  No Markdown highlighting; no "open with the system's
    program" for files that aren't text.
  - The Claude tab runs `claude -p` with --add-dir for the git root of every workspace solution and project
    (CIDEAskClaude::AddClaudeDirectories).

The index: CCPPIndex lives in CppCompilerLib.  Only the IDE and TestCppIndex use it; there is no command-line program
that indexes a solution and writes out what it found.

Claude: no repository has a CLAUDE.md.  What Claude knows of the project's decisions is mostly in about 195 memory

(the IDE's Claude tab starts in a solution or repository folder).  Claude Code doesn't load the CLAUDE.md of an
--add-dir folder unless CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 is set.

Files that aren't source (tracked, 2026-11-24): KiCad (HCP65: 260 schematics, 223 PCBs, 443 footprints; LogiCim: 23

Decided (the user's, 2026-11-24)
--------------------------------

 1. The IDE treats the Markdown docs as part of the code.
 2. Pages live next to the code they describe, each an item of that code's .vcxproj (one owning project per page),
    not all in one Website project ("This sounds much better").  Website.vcxproj keeps what belongs to the site as a
    whole.
 3. HCP65/Datasheets is excluded from the documentation: no project items, no references, no manifest.
 4. A file the website has replaced is deleted from the repository, and the page says which commit last had it.  Done
    for the cpy draft PDF (HCP65 c61cfa6).
 5. The 65C64's source of truth is X65C64-Proposal/65C64 Instruction Architecture.xlsx; the website is derived from
    it.  fscr and fccr were missing from its Instructions sheet and were added in red (HCP65 bd998c0).
 6. Find names: set / clear for bits, non-zero / zero for crumbs, nybbles and bytes (website: HCP65 db6ec74).
 7. Spreadsheet edits go through LibreOffice (installed 2026-11-24, 24.2.7.2, the version that writes the file).
 8. References to code are explicit (question 1): [`CTextArea`], [`CTextArea::ReplaceRanges`], [`BaseLib/Chars.h`].
 9. Owners (question 2): the 65C64 architecture pages live in X65C64-Proposal beside the spreadsheet, with a small
    Makefile project of their own there (X65C64-Proposal.vcxproj: the spreadsheet, its generators and the pages);
    the HCP65 hardware pages (memory map, registers, devices) live with HCP65Lib
    (HCP65-Emulator/HCP65Lib/Docs), whose devices implement them.
10. Project items are hand-listed, one per page (question 3), not wildcards.  The site build checks that every page
    under a mapped folder is an item of exactly one project, and fails (with the page's path) when one isn't.
11. Test data (a test's Input and Output folders) is owned by its test project by where it is, not as items
    (question 11): it isn't documentation, the tests find it by path, and Solution Explorer doesn't show it.
12. Links to code go to the branch (question 4): GitHub's blob/<branch>/<path>#L<line> with each repository's branch
    (CommonLibraries master, the others main), not pinned to a commit.  Line numbers can drift as files change until
    the site is rebuilt; accepted.
13. The map of docs folders lives in mkdocs.yml under extra.sources (question 5), not in a file of its own.  The IDE
    reads mkdocs.yml with a YAML parser in BaseLib (CYAMLParser, beside CXMLParser and CJSONParser, into the same
    CMarkup tree), so it can read nav: too.  CYAMLParser and CYAMLFile were built 2026-11-24 (CommonLibraries
    e11ce91e9, with CTextParser::SkipUTF8BOM fixed in 4a0a9da19): identical to PyYAML on this mkdocs.yml.
14. The command-line index program lives in HCP65-IDE beside HCP65Build (question 6): it reads solutions with
    VisualStudioLib, which is there; not in CppCompilerLib's tests.
15. Every ```cpp block compiles by default (question 7), check only: a block of statements is compiled inside a
    function; a page names its headers once in a hidden comment at its top; a block that mustn't compile is marked
    ```{.cpp .no-check} (it keeps its C++ colouring).  21 ```cpp blocks on 2026-11-24, about half statement fragments
    (sprites, assembler, refactoring pages).
16. Claude's memory notes move into the repositories (question 8), four kinds of them: the user's design rulings (to
    design pages and plans' decision lists), recipes (to CLAUDE.md files and testing pages), how the user wants
    Claude to work (to CLAUDE.md, so every session follows them, the IDE's Claude tab included) and status and
    handoffs (to the plan files).  Machine fixes and session history stay in memory; what stays becomes pointers.
17. A finished plan whose design page exists is superseded and deleted (question 9; decision 4's rule): the design
    page names the last commit that had it.  Only a fully finished plan: its open items move to the design page's
    "not done" list first (a plan kept as a gap list, like Navigation.txt, stays until then), and what points at it
    (other plans, notes, memory) is changed to point at the design page.
18. MCP tools for Claude (find definition, find usages including Documentation, the pages that cover a symbol) are
    served by the running IDE only, for now (question 10): its index is live and has unsaved edits.  A headless
    server (the decision 14 program) is not planned; add it only if sessions without the IDE need it.
19. Design pages are also written per area from Claude's memory notes, whether or not the area had a plan (G4), and
    the rest of H3 is done that way (the user, 2026-11-24, taking the recommendation): one area at a time, after A, B
    and D, its design notes becoming its design pages and its status notes their "what is built" and "not done" (or
    its plan's open items), then those notes deleted.  Largest areas first: WindowLib, the compiler, BaseLib and
    StandardLib, Assembler65Lib and Libc65, then the rest.
20. The indexing setup moves out of the IDE app into a library both the IDE and D1's program use, so they index a
    workspace identically (the user, 2026-11-24): HCP65-IDE/Libraries/IndexLib, CWorkspaceIndex (the configuration,
    the system headers, the projects' include folders and defines, the worker-thread indexing), from which the
    IDE's CIDECodeModel derives.


Proposed (my recommendations, not decided)
------------------------------------------

  - One site, built from many folders: each repository's Docs folders are gathered into a staging folder laid out as
    the site is today, so URLs and relative links between pages don't change.
  - References to code (explicit, decision 8) are written Rust style.  An unresolved one is a build error.  A plain code span that looks like a class (`CFoo`) and isn't a reference is
    a warning, which is also the worklist for converting the existing pages.
  - A reference becomes a GitHub link to the line on the repository's branch (decision 12).
  - Tables are generated, never written by hand, wherever a source exists: the spreadsheet for the 65C64, the KiCad
    netlists for the HCP65's memory map, registers and pinouts.
  - Examples are tests: every ```cpp block compiles (decision 15); longer code comes from test files through named
    snippet sections.
  - Designs: a finished plan becomes a design page (how it works + the decisions and why); the class's main header
    points at it in one line.
  - Not doing: Doxygen or generated API pages (they copy the headers and bring a second C++ parser), implicit
    references (Rename's text search found 106 unrelated Kills), per-repository sites, a home-made source browser.

E. The IDE treats docs as code (HCP65-IDE)
  Planned 2026-11-24 (the user: "Plan E please"); nothing built.  What there is (surveyed the same day):
    - Builds: CSolutionBuild picks one toolchain per solution (HCP65, MSVC or GCC) and each builds its projects'
      ClCompile items; ConfigurationType is only read to tell a static library.  Nothing runs a Makefile project's
      NMakeBuildCommandLine, so Website.sln (Website and X65C64-Proposal, both Makefile projects running
      `bash web.sh build|rebuild|clean`) can't be built from the IDE.  CCommandBuild runs programs in turn and
      collects their output; the Build pane and Problems list read GCC's "<file>:<line>:<column>: error:" lines
      (CIDEMessageOutput::ParseMessageLine), which is what web.sh's checks and code_references.py print.
    - Pages: an editor tab whose file is an item of a project is handed to the edits thread, which parses it as C++
      (CIDEEditorTab::TakeEdits, CIDECodeModel::ProcessEditedFile).  (Found while building: CIDEDocuments::
      AddEditedFile drops every file that isn't C or C++, so a .md item was plain text, never coloured as C++.)
      Rename's text search covers .md and .txt items (IDERename.cpp:267) as text, not as references.
    - The index: places carry a usage type (ECPPUsageType, CppCompilerLib); Find Usages groups by it; Rename edits
      the text at each place; Go to Definition starts from FindSymbolAt(file, line, column).
    - D's rules for what a reference names (overloads, parameters, enumerators, files) and where a code span is
      (fences, comments, link texts) are Python (tools/code_references.py, symbol_table.py).  The plan's rule is
      that one piece of code decides for the IDE and the site; today only the symbol table is shared.
    - Nothing opens a file with the system's program.
  1. Resolving moves into C++ (IndexLib), one implementation for the IDE and the site:
       a. CMarkdownSpans: a page's code spans outside fences and HTML comments, each with its line, column and what

Things to watch for
-------------------

  - Other sessions edit these repositories at the same time: check git status, commit only this work's files.
  - Generated files are never edited by hand; the generator is changed and rerun.
  - The staging folder must reproduce today's layout exactly or every relative link breaks: compare the built site's
    file list before and after each move.
  - A check reporting a staging path is useless to the IDE: always the page's real path.
  - Indexing every solution for D takes time (the IDE's startup indexing is about 10 s per large solution): cache the
    symbol table by commit.
  - The spreadsheet is edited with LibreOffice, not by rewriting its XML.
  - mkdocs strict mode: a `|` inside a code span in a table needs <code>..&#124;..</code>.
